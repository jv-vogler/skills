# Errors across the layers

An error has to survive three layers: a 401 from the network becomes "wrong password" on a
form. What must _not_ survive is prose — a message string is a terrible carrier, because the
view ends up parsing English to decide what to render.

The rule: **an error crossing a layer boundary carries a machine-readable discriminant.**
Copy is chosen at the very end, in the view.

## 1. Infrastructure: throw, do not interpret

The HTTP client throws on non-2xx, carrying the response. Endpoint functions let it
propagate. Infrastructure has no idea whether a 404 means "no such user" or "this feature is
off", so it must not decide.

The only thing infrastructure provides is a predicate for recognizing its own error type:

```ts
// src/infrastructure/httpClients/isHttpError.ts
export const isHttpError = (error: unknown): error is HttpError =>
  error instanceof HttpError;
```

Every layer that throws a distinguishable error exports a predicate like this alongside it.
That predicate is the contract; `instanceof` at the call site is not.

## 2. Domain: capture the failures you expect

The domain catches the failures it knows how to interpret — with the caught value's type
known — and lets everything else propagate untouched.

The baseline needs no dependencies:

```ts
let loginData: LoginResponse;

try {
  loginData = await infraLogin(payload);
} catch (error) {
  if (!isHttpError(error)) throw error; // not ours to interpret

  throw toLoginError(error);
}
```

The `if (!predicate) throw` line is the whole discipline. A bare `try/catch` without it
absorbs genuine bugs — a `TypeError` in the payload construction — into the same branch that
handles a 401, and reports both to the user as "wrong password".

`retex` is the ergonomic version of exactly that (see `helpers.md`): it turns a throwing
call into a tuple whose error element is typed by the predicates you pass, and it rethrows
anything none of them match.

```ts
const [loginData, loginError] = await retex(
  () => infraLogin(payload),
  [isHttpError],
);
```

`loginError` is `undefined` on success and an `HttpError` otherwise, so the success branch
needs no narrowing and the failure branch already knows what it has.

**`retex` is not `Result` / `Either`.** Nothing composes — there is no `map`, no `andThen`,
no short-circuiting chain — and unlisted failures still throw. It is a typed selective
`catch`, and treating it as a functional error monad leads to code that threads tuples
through call stacks that should have been throwing all along.

The rule worth teaching is the one underneath: **values inside a function, exceptions across
boundaries.** Within a function, a failure you can handle is just another value to branch
on. Crossing a layer boundary, throw — so a caller that forgot to handle the failure gets a
loud error rather than silently proceeding on `undefined`.

## 3. Domain: rethrow a typed error

The error the domain throws carries a `reason` from a closed union, plus the original error
as `cause`:

```ts
// src/domain/auth/login.ts
export async function login(
  credentials: LoginCredentials,
): Promise<Authentication> {
  const [loginData, loginError] = await retex(
    () =>
      infraLogin({
        username: credentials.taxId,
        password: credentials.password,
      }),
    [isHttpError],
  );

  if (loginError !== undefined) {
    if (loginError.response.status === 401) {
      throw new LoginError("Wrong password!", {
        reason: "WrongPassword",
        cause: loginError,
      });
    }

    throw new LoginError("Unexpected login error!", {
      reason: "UnexpectedError",
      cause: loginError,
    });
  }

  return {
    token: loginData.access_token,
    expiryDate: add(new Date(), { seconds: loginData.expires_in }),
  };
}
```

`LoginError` is a class with a typed `reason` and a matching guard — hand-written, or
generated by the factory in `helpers.md`.

Points worth being deliberate about:

- **The status→reason mapping happens here and only here.** This is the layer that knows
  what a 401 means for this operation. A different endpoint's 401 may mean something else
  entirely.
- **Always keep `cause`.** It is what makes the original stack and response reachable in
  error reporting. Losing it turns a debuggable failure into "Unexpected error!".
- **Always include an `UnexpectedError` reason.** Every failure gets a reason, so the view's
  mapping can stay exhaustive and no branch renders nothing.
- **The message string is for developers.** It is what shows in logs; the user never sees it.
- **Export the guard and the reason type always** (`isLoginError`, `LoginErrorReason`) —
  those are what the view imports. Export the class itself only if callers construct it.
- **Where the shape of the error matters more than its status**, inspect the payload: a
  lookup API that answers `{ error: true }` with a 200 gets `if ("error" in data) throw ...`
  in exactly the same place.

## 4. View: map reason to copy

The view converts `reason` into a message through a `Record` keyed by the reason union — so
adding a reason in the domain becomes a compile error until the copy exists:

```tsx
const getLoginErrorMessage = (error: Error) => {
  if (!isLoginError(error)) {
    return "Something went wrong. Please try again later.";
  }

  const loginErrorMessages: Record<LoginErrorReason, string> = {
    UnexpectedError: "Something went wrong. Please try again later.",
    WrongPassword: "Incorrect password.",
    UsernameDoesNotExist: "No account found. Please sign up first.",
  };

  return loginErrorMessages[error.reason];
};
```

That exhaustiveness is the whole return on the ceremony. A `switch` with a `default`, or an
`if/else` chain, silently absorbs new reasons and ships a blank error state.

The guard clause matters too: an error reaching this function might not be a `LoginError` at
all — a network failure, a bug in the mapping code — so there is a fallback before any
assumption about `reason`.

User-facing copy lives in the view, in the product's language. Domain messages stay in
English, for developers.

## 5. Schema validation is a tripwire, not a gate

Response schemas are validated, logged on failure, and then the data is used anyway:

```ts
const { error } = GetProductResponseSchema.safeParse(data);

if (error) {
  console.error(error);
}

return data as GetProductResponse;
```

This looks wrong at first glance and is deliberate. A backend adding a field, or loosening a
nullability that the app never reads, should not white-screen a page — but the drift has to
be visible, immediately, in the console and in error reporting. Blocking would trade a
working page for an outage every time the two sides deploy out of step.

Use the throwing variant where continuing is genuinely worse than failing — an auth token
response, a payment confirmation — where malformed data would put the app into a state worse
than an error screen.

The `as` cast is the honest consequence: validation is advisory, so the compiler is being
told what the contract _says_. Reserve it for exactly this spot.

## 6. Typed errors vs. bare throws

Not everything deserves a typed error. Invariant violations — the ones that mean the code is
wrong, not that the world misbehaved — throw plain `Error`s with a message naming what was
expected:

```ts
throw new Error(
  `Expected checkout flow to be at step ${expected} but it was in ${actual} instead!`,
);
```

These are used by `useGuaranteedX`, `useXFlowAtStep`, route-param hooks, and context hooks
called outside their provider. Nobody catches them, and nobody should: they are assertions,
and they fail loudly in development and reach error reporting in production.

The distinction to hold on to: **a typed error is for a failure the user needs explained; a
bare throw is for a state that should have been impossible.** Reaching for a `reason` union
on an invariant just adds ceremony to something no one will ever branch on.
